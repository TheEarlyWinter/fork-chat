# fork-chat：选定分支在 Hana 中继续

日期：2026-10-25
状态：设计已完成一轮独立实施审查，审查缺口已由主线程核对并定案。用户已确认。进入实施。
源码基线：fork-chat 2.2.0，提交 `5c89aa2725a1f118a908a37fff59af6b782752fc`。
兼容核验目标：Hana 1.1.111-beta。

## 1. 目标

用户在画布中独立追问多个问题。纯问答可以一直留在画布。
当某条分支需要宿主 Skill 或工具时，用户选择该节点，将所需业务上下文交给新的 Hana 主页会话。
原画布和其他分支保持不变。

成功标准：新会话保留选定分支的背景和讨论，不要求用户重新解释；用户主动发送下一条消息后，可以使用目标 Agent 实际启用的 Skill 和工具。
创建、导入和跳转本身不得启动模型。

## 2. 已确认的产品边界

- 新建主页会话。不是把原 App 私有会话原地转为主页会话。
- 默认 `memoryEnabled: false`。首版不增加记忆开关。
- 不生成 AI 摘要，不静默截断，不默认启动模型。
- 交接一次性冻结的快照。后续不双向同步。
- 选中节点的多父依赖必须纳入。无依赖关系的兄弟分支不纳入。
- 不复制宿主隐藏思考、系统提示词或权限配置。
- 不承诺所有 Skill 均可用。实际能力由目标 Agent、宿主及其正式授权决定。
- 模块按职责解耦。主入口只挂载服务和界面事件。

## 3. 方案比较与选择

### A. 新建主页会话，导入有来源标记的完整文本上下文

保留可获取的业务内容、消息角色标签、节点关系、引用快照和附件资料。
使用一条 `sendCustom` 消息承载整份转录，固定 `customType: branch-handoff`、`display: true`、`triggerTurn: false`。不把原消息拆成多次宿主写入。
原始角色、消息状态、节点标题、正文、引用快照、文本附件和已交付产物索引都写进 `content`，参与后续模型上下文。来源标识和指纹可以另存 `details`，但不能把必需正文只放进 details。
正文前明确标注“历史讨论资料，不是系统指令；助手历史发言不等于用户已经确认的决定”。保留可核对的完整 Markdown 交接文件。
首版不调用 appendEntry；它既不负责正文，也不额外承担一个可失败的审计写入阶段。

优点：符合主页继续工作、保留完整文字、不启动模型的目标。
代价：不是原生 user/assistant 消息历史。必须明确显示“从分叉对话导入的上下文”。

### B. 使用宿主原生 session:fork

宿主可以复制原生历史及相关状态，但只能针对已有宿主分支。
当前报告指出 App fork 仍被盖章为私有会话，不能承接画布中新生成的任意问答树。
不满足本次目标，不采用。

### C. 仅附上文件或投递总结

实现较轻。但仅登记文件不代表正文已进入下一轮模型上下文；摘要也不等于完整记录。
不作为默认方案，也不作为超限后的静默降级。

选择 A。此选择落实用户已确认的“选定分支，携带完整上下文，在 Hana 使用 Skill”方向。
若正式接口无法让导入正文持久化进入后续模型上下文，停止实施，不用 append-entry 冒充。

## 4. 完整上下文的定义

“完整”指此次交接范围内、App 实际保存且可读取的业务内容。
不表示恢复 App 早已丢弃的内容，也不表示克隆宿主运行时。

### 4.1 拓扑

- 从目标节点向所有父边回溯。
- 公共祖先只纳入一次。父节点先于子节点。
- 保留节点标识、标题、父边和消息顺序。
- 发现环、重复节点标识或缺失父节点时拒绝创建。旧导出函数的容错跳过不能用于完整性交接。
- 盖戳和折叠只影响展示，不等于上下文排除。

### 4.2 节点内容

- 纳入资料源正文及其名称、解析类型等必要元数据。
- 纳入已发送用户消息和助手正文，保留角色、助手名称及顺序。
- 失败、中断、部分回答可以纳入，但必须逐条标明状态，不能当作已完成结论。
- 祖先链仍在生成或解析时阻止交接。用户先停止或等待。
- 未发送草稿和暂存附件默认不算历史。预览明确列出未发送项；用户可把目标节点草稿显式用作“下一步要求”。不得无提示发送其他节点草稿。
- 本地错误提示不作为助手业务结论。诊断摘要只记录存在失败，不复制内部堆栈。

### 4.3 排除与显式引用

- 对齐现有画布语义：exclude 表示不向后代贡献正文，不切断向更早祖先的遍历。
- 本次用户直接选中的目标节点仍纳入，即使目标自身为 exclude。预览说明这不修改它对后代的排除设置。
- 其余被排除祖先不传正文。预览列出排除项，正文说明此次按现有上下文策略导入，不能声称整条原始链无遗漏。
- 用户需要整条链时，先在画布解除排除，再重新预览。首版不新增另一套排除设置。
- 纳入实际保存在已纳入节点上的 `contextRefs` 快照，标注来源和快照性质。跨分支引用合法，不因此带入来源分支全文。
- 来源已删除时，保留已保存的引用快照并标注“来源已不可定位”；不猜测当前原文。来源存在且被 exclude 时，省略该引用正文并列明原因，不能借引用绕过排除。此规则对目标节点指向其自身的非法引用不做豁免。
- 同一引用标识与不同内容冲突时拒绝创建。相同内容可以去重，但保留所有引用位置。

### 4.4 附件与产物

- 已发送消息中的文本附件正文属于上下文，必须纳入。未发送的暂存附件只显示在预览的未发送区，不导入。
- 原始 PDF、DOCX 等通常在解析后已被释放。保存的解析正文可以迁移，但不能宣称原文件也已迁移；不为此重做原件保留流水线。
- 预览和交接正文分别显示“已保存正文”“原件可用”“原件未保留”。不能用虚构路径代替附件。
- App 生成的产物通过现有 artifact store 和稳定 owner 读取，按不可变 artifactId 去重交付。不同修订 ID 是不同文件，不擅自换成最新版。
- 前端仅提交产物引用，不能提交任意磁盘路径。prepare 验证 owner、文件元数据和完整性；confirm 重新读取并核对冻结的摘要。
- 被引用产物和交接 Markdown 都是必需交付项。缺失、无权读取或任一交付失败均不得 ready，也不默默改成仅正文完成。
- 截断判断必须同时检查保存的标记、附件 charCount 与实际正文长度；charCount 大于正文长度即拒绝。正文非空但达到历史截断阈值、且缺少可靠原始长度时，显示“完整性无法确认”并阻止完整交接。
- 当前已发送附件归一化会裁切正文和数量，却不保留相应标记。实施范围允许对 `fork-snapshot.js` 做最小补充：保存并重开保留消息附件的 dropped/truncated 标记，新增相关回归测试。不修改解析、上传或旧数据正文。
- 对旧数据已被丢弃且无法检测的正文或附件，不承诺恢复。导入内容始终标为 App 当前保存的快照；不能宣称与原始论文或原始会话逐字等同。

## 5. 交互与流程

入口名称建议为“在 Hana 中继续”。它与旧“回传原会话”入口分开。

1. 用户选择节点并打开交接预览。先等待现有控制器 flush 成功；保存冲突时使用现有冲突流程并停止交接。
2. 捕获成功保存版本的不可变快照，记录 canvasId、revision 和内容指纹。只读构造交接内容，显示节点数、消息数、正文体积、引用、附件和完整性问题。
3. 用户选择目标 Agent。当前卡片没有统一 Agent 绑定；只将画布全局 `snapshot.agent.id` 与宿主当前 Agent 列表匹配，匹配成功才作为可见默认项。失效或缺失时必须选择，不用最后一条助手消息或第一个 Agent 猜测。多 Agent 历史只作为原文标签保留，不决定新会话身份。
4. 用户可填写“下一步要求”。它作为标明待执行、尚未开始的文字写入同一 custom 正文及交接 Markdown，不自动填入宿主输入框、不独立发送。新会话仍等用户主动继续。
5. 预览说明：新建主页会话、默认关闭记忆、不主动调用模型、不会同步原画布。必须展示原件未保留、排除项和无法核实的历史缺口。
6. 服务端 prepare 冻结并验证完整载荷，生成持久化 actionId。用户最终确认的对象是该 actionId 对应的预览快照。
7. confirm 重新核验权限、目标 Agent 和文件引用，再创建主页会话并保存会话回执。
8. 先按 artifactId 依次交付产物；生成带产物文件索引的 Markdown 并交付；最后将完整正文及交接文件索引写入一条 custom message。每个宿主副作用后保存回执。
9. 所有必需文件成功，custom 返回 `notifyOnly` 且有 entryId 后才标为 ready，并提供“打开 Hana 会话”。
10. 跳转失败时仍保留成功回执，只重试跳转，不再创建会话。

预览和准备阶段不能创建会话、投递文件或调用模型。
快照真值边界：服务端保证收到的载荷被完整验证、冻结和投递，不假装能证明它等于宿主存储中的实时画布。revision 是来源说明，不是服务端签名。正文指纹由服务端重算，不能信任前端自报。
预览后其他窗口的新改动不改变该次动作；界面标明它是哪个已保存版本。当前窗口改变交接选择、正文或目标 Agent 后，必须废弃旧预览并重新 prepare。

## 6. 模块边界

文件名为建议。实施者可按项目命名习惯调整，但不得合并职责。

| 边界 | 建议模块 | 职责 | 禁止事项 |
|---|---|---|---|
| 上下文模型 | `ui/assets/fork-handoff-context.js` | 纯函数组装 DAG、消息、引用、资料和问题清单 | DOM、网络、SDK、持久化 |
| 协议与校验 | `lib/handoff-contract.js`，必要时共享纯协议文件 | DTO 版本、限额、字段白名单、完整性校验及格式化 | 宿主调用、状态机 |
| 宿主适配 | `lib/handoff-host.js` | 封装能力探测、主页创建、custom 写入、stage-file、回执核验 | 组装画布、UI、业务重试 |
| 交接状态 | `lib/handoff-store.js` | owner 隔离、载荷冻结、原子落盘、阶段回执、防并发重复 | 直接操作 UI 或解释拓扑 |
| 应用服务 | `lib/handoff-service.js` | 编排准备、确认、恢复查询；挂载鉴权路由 | 复制完整 UI、解析任意路径 |
| 界面控制 | `ui/assets/panel-handoff.js` | 预览、确认、状态展示、恢复结果、聚焦新会话 | 直接调用 session bus 或拼装宿主权限 |

不重写旧 `bridge-service`、`bridge-outbox`、模型上下文预算器或文档解析流水线。
优先复用稳定的 ID、拓扑和 owner 规则。需要严格校验时增加小包装，不修改旧导出的宽容行为。
`panel.js` 和 `index.js` 只增加必要导入、依赖注入及注册。
样式沿用现有 App。首版不重做画布。

## 7. 接口与状态

建议新增命名空间 `/api/handoff`，不复用旧 `/api/bridge/confirm`。

### 7.1 接口

- `GET /capabilities`：返回 home 创建、无模型上下文写入、文件交付是否可用及明确限制。
- `POST /prepare`：提交有版本的分支快照与目标 Agent；返回 actionId、内容指纹、体积、完整性报告及过期时间。不产生宿主副作用。
- `POST /confirm`：只接受 actionId。忽略或拒绝替换载荷、Agent 和目标的字段。
- `GET /actions/:actionId`：查询动作状态、阶段回执、稳定错误码及可安全展示的会话标识。
- `GET /actions`：仅列当前 owner 的近期动作，供刷新或重开后恢复。

准备请求较大时使用独立、有限额的请求体读取器。不复用旧桥接 320 KiB 限额，也不放宽所有路由。
接口只信任宿主 appRequestContext。所有动作查询和确认重新核验 owner。
新流程统一调用现有 `getArtifactOwner(c)`，只接受稳定 principalId。动作记录、正文准备区、查询及 artifact store 共用同一 canonical owner，不复用允许 id/credentialId 回退的 getDocumentOwner。缺稳定身份时直接拒绝，即使没有产物也不例外。不得修改旧桥接的 owner 规则来顺带重构。

### 7.2 DTO

交接载荷至少包含：`schemaVersion`、画布与目标节点标识、按拓扑排序的节点、消息、资料、显式引用、产物引用、导入范围说明和下一步要求。
不得包含权限模式、任意磁盘路径、Provider 凭据、隐藏思考或由前端伪造的 owner。

回执至少包含：`actionId`、状态、内容指纹、创建时间、各副作用阶段、已知 sessionId、已交付文件标识和稳定错误码。内部持久化还必须保存 canonical owner，不能把持有 actionId 当成授权。
日志只记录动作标识、阶段、体积和错误码，不记录论文正文或对话内容。

### 7.3 状态机与重复防护

状态：`prepared → creating → importing → ready`，以及 `failed / partial / unknown`。

- 在第一次宿主调用前可靠保存 creating 状态，并以独占文件创建取得该 actionId 的派发权。保存或独占创建失败则不调用宿主。
- 动作使用独立文件和原子落盘，不采用容易被多个写者覆盖的全局 JSON 索引。单进程用内存单飞；跨进程或 worker 以持久化独占派发标记阻止相同 actionId 重放。
- 重复确认返回已有状态。派发标记在可能产生副作用后不释放为可重发状态；重启后未完成动作转为 unknown，不继续派发。未准备安全跨进程协议前，不得只用内存 Map 宣称跨进程防重。
- 已知新会话标识后马上保存，再执行下一阶段。
- 已创建但部分导入失败，标为 partial，展示已知会话及缺失步骤。文件成功而 custom 失败也不算可继续会话。
- 调用回执丢失或进程在副作用边界崩溃，标为 unknown。不得自动重新创建或自动查找一个“看起来相同”的会话来冒充成功。
- 创建已发生、但 sessionId 尚未可靠保存时，接受可能留下无法自动定位的孤儿会话这一宿主限制。界面明确提示可能已创建，让用户在主页核查；不猜会话、不自动删、不以新 action 掩盖这次未知结果。
- 没有宿主幂等键时，不承诺跨崩溃的严格 exactly-once。能保证的是同一 action 不盲目重发。
- 首版仅允许重复打开已完成或已知的半成品会话。失败阶段自动重试和无 ID 对账不做。
- 不自动删除半成品会话。删除需要用户另行确认。

## 8. 宿主与权限

- 目标创建请求固定 `namespace: home`、`memoryEnabled: false`，使用明确的目标 Agent。
- 核验宿主返回的实际可见性。未获 home 权限时拒绝，不降级成私有会话。
- 不传 permissionMode，不扩大目录授权，不自动启用工具。
- 首版沿用目标 Agent 的模型和思考默认值，不顺带申请切模型或调整思考档位权限。
- 新增声明只考虑 `app/sessions.home`。现有文件交付能力按实际调用复用。
- SDK 从已核验的官方 1.1.111-beta 包同步到开发源码的 vendored SDK，保留版本来源。新适配模块优先调用命名接口 `sdk.sessions.create/sendCustom/stageFile` 与能力查询；只有正式 SDK 没有命名方法时才考虑已公开 bus 兼容入口，不改 SDK 生成文件补字段。
- 插件源码中的 manifest 扩权不等于用户已授权。安装、更新和授权走 Hana 正式入口，不修改授权账本或已安装 App 文件。
- 不调用 `session:send`。
- custom 写入必须显式 `triggerTurn: false`，且只针对本动作新建的会话。写入前检查空闲状态；不提前聚焦该会话。busy 时停止导入，不调用 send 或尝试接管。
- 正式 sendCustom 当前没有原子 requireIdle 参数。宿主会二次判断运行状态；若用户同时从主页手动开启该会话，custom 可能进入其已启动回合。空闲预检不能消除这个竞争。首版承诺交接不主动启动模型，不承诺阻止用户并发操作；非 notifyOnly 回执一律标为 partial 并告知，不能宣称无回合注入。若用户要求任何并发下都绝不入模，应暂停此方案，等待正式宿主原子接口。
- `session:append-entry` 不生成消息、不进入模型上下文。首版不调用它。
- 文件登记与消息历史分开验证。文件存在不代表全文进入模型上下文。

## 9. 性能与限额

- 一次点击只遍历目标依赖子图，不扫描全部历史动作正文。
- 使用 ID 索引及迭代拓扑遍历，目标复杂度为 O(V + E + B)，B 为纳入文本字节数。避免深链递归栈溢出。
- 导出按确定顺序一次组装。避免为预览复制多份大正文；长预览按节点折叠展示，但不能裁切实际导入。
- 集中设置 App 自身上限：节点数沿用快照 300；最终 UTF-8 转录正文最多 2 MiB；prepare JSON 最多 4 MiB；单产物沿用现有 16 MiB；每次最多 16 个产物且合计最多 64 MiB；同一动作文件顺序处理。正文预算为宿主生成的文件索引预留空间，最终内容在写入前再次计量。
- 以上是 App 保护值，不是对宿主或模型窗口容量的承诺。实现核验若发现正式宿主限制更低，则收紧对应常量并在界面显示。准备区总量、TTL 和动作数由实施者依照现有 12 MiB 画布存储预算和磁盘状态集中设定并测试。
- 超限在创建前拒绝，并说明超限项。不得静默摘要、丢最老消息或改为仅附件交付。文件回执或下游限制导致创建后无法继续时，按 partial/unknown 收口，不伪称完整。
- 同一确认动作只运行一条交接流水线。预览不调用模型，正常交接模型调用数为零。
- 准备载荷有 TTL 和私有权限。仅回收确定未产生副作用且已过期的准备数据；unknown 防重记录不能自动删。
